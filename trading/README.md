# 題材回檔量增策略（模擬單）

跟專案主線（`fetch_daily.py` 那套資料管線）完全隔離的獨立模組。**目前只能下模擬單**，沒有使用者
明確確認絕對不會變成真單——見下面「安全閘門」。

## 策略規則

**進場（四個條件同時成立才進場）**

1. **題材一致性**：該股所屬 `concept_map` 題材的中位數漲跌幅 > 0（題材正在發酵）
2. **回檔至支撐**：收盤價落在 MA5(周線)／MA20(月線)／MA60(季線)**任一條**的 ±2% 範圍內（回檔找支撐，
   不是追高）
3. **量增確認**：Shioaji 快照的 `volume_ratio`（量比）≥ 1.5 倍——這是**相對值**（今天 vs 自己過去5天
   均量），薄盤股在很小的絕對量基礎上也能衝出高倍數，所以還需要條件4補一個絕對門檻
4. **流動性門檻**：當日累積成交金額（Shioaji 快照的 `total_amount`）≥ NT$1億——用成交**金額**而不是
   張數/股數，因為不同股價區間的張數門檻天生不同（股價200元的股票，同樣金額只需股價20元股票的1/10
   張數），金額可以跨股價區間公平比較，也是機構篩股常用的流動性衡量方式

**出場（任一條件觸發就出場）**

- 停損：未實現報酬 ≤ -5%
- 停利：未實現報酬 ≥ +10%
- 持有超過 5 個交易日（一週）
- 題材轉弱：該股題材的中位數漲跌幅轉負

**資金**：每筆買 1 張（整股，1000股），金額隨股價浮動；所有**持倉中**的部位總成本（進場價×股數加總）
不能超過 **NT$600,000**——新訊號如果會讓總成本超過上限，就跳過不買（會列在報告的「資金上限已滿」區塊），
單一股票如果 1 張成本就超過 60 萬（股價>600），也會被同一個檢查自動擋掉。

### 多檔同時符合三條件、資金不夠全買時，怎麼決定優先買誰

不是照股票代號順序買（舊版是這樣，純屬巧合，跟訊號強弱無關）。改成每天把所有通過三條件的候選股，
依三個因子算出一個**加權總分**，分數高的先買：

- 題材強度 50%：所屬 `concept_map` 題材當天中位數漲跌幅，越強越優先
- 量增幅度 35%：`volume_ratio`（量比）越大越優先
- 回檔精準度 15%：收盤價離最近一條 MA5/20/60 的相對距離，越貼近越優先（跟「是否落在±2%內」的及格線是兩回事，這裡比的是精準度而不是及格與否）

三個因子各自在「當天所有候選股」之間做 min-max 正規化（0~1），不是對一個固定門檻比較——因為題材漲幅、
量比都沒有自然上限，只在當天候選池裡比較相對強弱才有意義。權重在 `config.py` 的 `RANK_WEIGHTS`，
排序邏輯在 `signals.rank_candidates()`，每日報告的「新進場訊號」「資金上限已滿跳過」都會附上排序分數。

### 為什麼是整股，不是零股

一開始做的是零股（可以精準控制每筆金額在 NT$20,000），但零股**盤中每 3 分鐘才撮合一次**，實測買完
馬上想賣會直接被拒單（`集保賣出餘股數不足`），停損停利沒辦法像整股一樣即時成交。改成整股後進出都在
正常連續撮合的時段，犧牲的是「金額精準度」（1張成本隨股價變動，不是固定20000），用總成本上限
（600,000）控管整體風險而不是單筆金額。

## 執行節奏

- **盤中**（建議跟 `build_dashboard_live.py` 同樣每分鐘排程）：`intraday_monitor.py` 只檢查**已持倉**
  部位的停損/停利（這兩個需要即時價，等不到收盤）
- **收盤後**：`daily_scan.py` 掃描全部 `concept_map` 股票的三個進場條件、檢查持有天數/題材轉弱出場、
  寫出當日報告（`trading/reports/YYYY-MM-DD.txt`）

```bash
python -m trading.daily_scan
python -m trading.intraday_monitor
```

## 安全閘門（最重要的部分）

`executor.py` 的下單函式永遠先檢查兩個條件，**缺一都還是模擬單**：

1. 命令列有 `--live`
2. `.env` 裡 `TRADING_LIVE_CONFIRM` 設成完全等於 `I_UNDERSTAND_THIS_PLACES_REAL_ORDERS`

```bash
# 模擬（預設，安全）
python -m trading.daily_scan

# 想要真的上線時（兩步都要做，缺一不會變成真單）：
# 1. .env 裡加一行：TRADING_LIVE_CONFIRM=I_UNDERSTAND_THIS_PLACES_REAL_ORDERS
# 2. python -m trading.daily_scan --live
```

每次執行都會印出目前是 `simulation (no real money)` 還是 `LIVE - REAL ORDERS`，不要只看有沒有錯誤訊息，
執行前先看這一行確認模式對不對。

## API 金鑰

下單需要**有交易權限**的那組金鑰（`.env` 裡的 `SHIOAJI_API_KEY_all`/`SHIOAJI_SECRET_KEY_all`），
不是 `realtime_quote.py`/`build_dashboard_live.py` 用的那組（那組是刻意只開「行情/資料」權限，拿去
下單會被 Shioaji 擋掉：`401 Token doesn't have permission`）。

另外，永豐證券帳戶第一次用 API 下單前，需要先完成**憑證簽署/啟用**（Shioaji 的 `activate_ca()` 或在
永豐金平台完成同意書），沒做的話下單會收到 `406 Please sign <帳號> first`——這是帳戶層級的一次性設定，
需要使用者自己用自己的憑證完成，不是程式碼問題。

## 檔案結構

- `config.py` — 所有可調參數（金額、停損停利%、持有天數上限、量比門檻、均線容忍帶）
- `signals.py` — 進場/出場判斷邏輯，純函式，不碰 Shioaji/資料庫，可以用假資料單元測試
- `ma_data.py` — 用 Shioaji `kbars()`（分K）resample 成日K，算 MA5/20/60
- `positions.py` — 模擬持倉記錄（`positions_state.json`，gitignore），開倉/平倉/算持有天數
- `executor.py` — Shioaji 下單包裝 + 安全閘門（見上）
- `daily_scan.py` — 收盤後主程式
- `intraday_monitor.py` — 盤中主程式（只檢查已持倉的停損停利）
- `report.py` — 產生當日文字報告
