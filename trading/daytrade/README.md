# 開盤區間突破當沖策略（模擬單，草案）

跟 `trading/`（波段策略）平行的獨立子模組，重用其 `executor.py`（登入安全閘門、下單）跟 `positions.py`
（持倉記錄，透過自己的 `positions_state.json` 跟波段完全分開），但訊號邏輯、資金池、排程都是獨立的。

**目前只能下模擬單**——安全閘門跟波段共用同一套機制（見 `trading/executor.py`），沒有使用者明確確認
絕對不會變成真單。

## 為什麼資料來源是分鐘K，不是即時快照

這支程式設計成每1分鐘重新執行一次（跟 `build_dashboard_live.py` 排程同頻率）。波段策略用 Shioaji 的
`snapshot()`（`volume_ratio` 是跟過去5天的日均量比、`total_amount` 是當日累計金額）——這些都是「日對日」
的相對值，不是分鐘級的。當沖既然每分鐘重跑，訊號就應該看「這一分鐘」真正發生了什麼，所以全部改用
`api.kbars()` 抓當天的1分鐘K線（`minute_data.py`），每次重跑都用當天完整的分鐘K現場重新計算：

- **開盤區間**：09:00開盤後5分鐘內的最高價。因為每次都重新從分鐘K算，不用自己維護一個跨輪詢的狀態檔
  去追蹤「目前看到的最高價」——用當天的K線資料本身就是最新的，不會因為漏了某次輪詢而算錯或過時。
- **量增確認**：最新一根分鐘K的成交量，相對「當天其他分鐘K平均量」的比值（不是Shioaji快照的日對日量比）。
- **流動性門檻**：當天所有分鐘K的成交金額（`Amount`欄位）加總。

## 每日觀察清單——為什麼不直接掃全市場或concept_map

2026-10-08用過去1個月、`concept_map`171檔題材股回測，純價格報酬平均只有-0.06%（幾乎無方向性優勢），
72%的交易靠強制平倉收場、不是停損停利。追查下去：`concept_map`是因為「業務關係」才被歸類進某個題材
（例如某公司做車用電子），不是因為它流動性好或股價容易大幅波動——很多題材股其實是冷門小型股，ORB
訊號在這些股票上常常只是雜訊，開盤區間本身很平淡，之後也沒有延續性。

改成**每天開盤前，用前一天的全市場資料選出當天真正適合當沖的股票**，放進`watchlist_state.json`：

- **範圍**：全市場（`company_info`，~2000檔，排除權證/ETF），不是`concept_map`
- **評分**：流動性（前一天成交金額）70% + 振幅（前一天(最高價-最低價)/開盤價）30%，兩者在當天全市場
  候選股之間各自做min-max正規化後加權（跟波段策略的候選排序是同一套手法，見`trading/README.md`）
- **取前30檔**：`config.WATCHLIST_SIZE`
- 全市場掃描很慢（~2000檔分鐘K，約10-12分鐘），所以**獨立一支程式`build_watchlist.py`在開盤前跑一次**，
  不是在`daytrade_monitor.py`裡每分鐘重算

`daytrade_monitor.py`每分鐘只讀`watchlist_state.json`的快取（快），不會自己重新掃全市場；如果快取
是今天以外的日期（忘了跑/跑失敗），只檢查既有持倉的出場，不開新倉，並印警告。

## 多空雙向（融券放空）

`--signal reversal_both`會同時檢查多空兩種K棒反轉型態，哪個成立就往哪個方向進場，一次只會成立
一種（兩種型態的K棒形狀互斥）：

- **多方**：錘子線 / 多方吞噬型態 → `executor.buy()`現股買進
- **空方**：射擊之星（倒錘子線：小實體靠近區間下緣、長上影線）/ 空方吞噬型態 → `executor.short_sell()`
  融券賣出進場，`executor.cover_buy()`融資買進回補出場——使用者指定的機制（融券開、融資平），
  不是自創

出場的停損停利方向會依多空自動反過來判斷（`signals.check_exit()`的`side`參數：空單「跌=賺、
漲=賠」）。**融券的借券費/利息等額外成本目前沒有建模**（不同股票費率差異很大、不確定性高），
回測的空單淨損益用跟現股當沖一樣的手續費/證交稅結構近似，實際成本可能略高於回測數字。

## 策略規則

**進場（四個條件同時成立，且還沒過強制平倉時間，且股票在今天的觀察清單裡）**

1. **開盤區間突破（ORB）**：最新分鐘K收盤價 > 開盤後5分鐘內的最高價（開盤區間不滿5分鐘前視為尚未成形，
   不判斷突破）
2. **量增確認**：最新分鐘K成交量 ÷ 當天其他分鐘K平均量 ≥ 3.0倍（原為2.0倍，回測後提高）
3. **流動性門檻**：當天累積成交金額 ≥ NT$1億
4. **開盤區間幅度門檻（新增）**：開盤區間本身的(最高-最低)/最低 ≥ 1%——排除開盤就很平淡的股票，
   即使之後觸發突破也沒有意義

13:00（強制平倉時間）之後即使訊號成立也不再開新倉——下一分鐘就會被強制平倉規則賣掉，白白付價差。

**出場（任一條件觸發就出場）**

- 停損：未實現報酬 ≤ -2%
- 停利：未實現報酬 ≥ +3%
- 強制平倉：最新分鐘K的時間 ≥ 13:00（不論損益，當天一定要平倉，不留倉過夜）

**資金**：每筆1張（整股1000股），跟波段策略分開獨立的資金池，總持倉成本上限 NT$600,000
（`trading/daytrade/config.py`，不是共用波段的額度）。多檔同時突破、資金不夠全買時，依量增幅度
（volume_ratio）由大到小排序優先買——當沖沒有題材/均線距離這些波段才有的因子，量能爆發程度是唯一
現成的強弱指標。

## 執行節奏

現在是兩支程式分工：

```bash
python -m trading.daytrade.build_watchlist      # 開盤前跑一次，約10-12分鐘（全市場掃描）
python -m trading.daytrade.daytrade_monitor      # 09:00-13:05 每分鐘重跑一次（讀watchlist快取，快）
```

排程：`TWTradingDaytradeWatchlist`平日08:30跑一次；`TWTradingDaytradeMonitor`平日09:00-13:05每1分鐘。

## 訊號比較（研究用，尚未決定要不要換掉ORB）

2026-10全市場watchlist回測後確認：ORB突破本身在這個時間窗沒有統計優勢。`patterns.py`實作了三種
不同的「方向判斷」邏輯，`backtest.py`可以在同一份資料、同一套量增/流動性門檻下，把ORB跟這三種
一起比較（只有「要不要進場」的判斷邏輯不同，其他條件完全一樣，才能公平比較）：

- **K棒反轉型態**：錘子線（下影線長、小實體在上緣）或吞噬型態（這根陽線完全蓋住前一根陰線）
- **連續同向K棒**：最新N根都是陽線且最高價一根比一根高（動能確認，不是反轉）
- **滾動範圍突破**：類似ORB，但「整理區間」隨時間滑動，不是固定釘在開盤前5分鐘

跑法：`python -m trading.daytrade.backtest --days 30` 會自動把四種訊號都跑一次並列出比較表。
**目前還沒有把任何一種訂為正式規則**——哪種訊號要拿去用，要等比較回測結果出來、跟使用者確認後，
再回來更新上面的「策略規則」區塊跟`trading/decisions.json`。

## 新聞題材選股（實驗中，未排程）

跟流動性/振幅選股是兩套**互斥的**選股方式（透過`--source`切換），搭配K棒反轉型態判斷進場時機
（`--signal reversal`）：

```bash
python -m trading.daytrade.daytrade_monitor --source news --signal reversal
```

流程：
1. 搜尋「前一日收盤後到當日開盤前」發布的利多新聞（目前這一步要Claude在場用WebSearch/WebFetch做，
   還沒自動化——`news_watchlist.py`的docstring有說明為什麼，以及之後怎麼轉成agent自動觸發）
2. 統計被提及個股的跨來源討論度，取討論度最高的5檔（`config.NEWS_WATCHLIST_SIZE`），存進
   `news_watchlist_state.json`（跟`watchlist_state.json`一樣的「寫一次、每分鐘讀快取」模式）
3. `daytrade_monitor.py --source news`改讀這份清單，`--signal reversal`改用`patterns.py`的
   K棒反轉型態判斷進場，而不是ORB

**還沒排程**——新聞搜尋沒有自動化前，排程了也只會一直吃到舊快取（會被`load_cache()`的日期檢查正確
擋掉，不會誤用舊資料，但也不會真的工作）。現有的`TWTradingDaytradeMonitor`排程沒有受影響，預設
參數（`--source liquidity --signal orb`）跟改動前完全一樣。

### 新聞選股：API路線 vs 不限管道路線

`news_api.py`是**可程式化、未來agent可以直接呼叫**的版本——用鉅亨網(cnyes)免金鑰公開新聞API
（`api.cnyes.com/media/api/v1/newslist/category/tw_stock_news`，確認支援`startAt`/`endAt`歷史
日期查詢，而且每篇文章本身就帶股票代號標籤），依「窗口內文章提及次數」排序選股，不需要Claude
在場搜尋。跟`news_watchlist.py`的手動WebSearch路線（不限管道、人工交叉比對）在同10個交易日比較
過（2026-10-12，結果見`trading/decisions.json`）：**兩條路線都是虧損的**，而且API路線因為用
「文章提及次數」排序，容易過度集中到台積電、台塑集團這類到處都會被提到的大型權值股，不代表真的
有當天的特定利多題材——用這個API時最好排除或降權處理超大型權值股。

## 單一個股選股：AI供應鏈 + 大量 + 新聞熱度

跟其他`--source`不同，這個模式只選**一檔**股票（不是清單），三個條件依序篩選：

```bash
python -m trading.daytrade.daytrade_monitor --source ai_chain --signal reversal
```

1. **AI供應鏈成分股**：`concept_map`的「AI伺服器」題材（目前9檔：台達電/鴻海/智邦/英業達/技嘉/
   廣達/緯創/神達/緯穎）——沒有擴大到ABF載板/PCB/封測等其他AI相關聯題材，範圍就是這9檔
2. **前一天大量**：成交金額需達 `config.AI_CHAIN_MIN_VOLUME_NTD`（NT$1億，沿用既有流動性門檻慣例）
3. **新聞熱度最高**：通過前兩關的候選股裡，窗口內（前一天收盤→當天開盤）cnyes新聞提及次數最高者勝出
   （沒有候選股被新聞提到時，退而選成交金額最高者，並在log中說明是哪種情況）

因為只需要檢查9檔的量+1次新聞API呼叫，很快（幾秒鐘），不像流動性清單的全市場掃描要10幾分鐘，
所以**不需要獨立的開盤前排程**——`daytrade_monitor.py`第一次執行時發現沒有今天的快取
（`ai_chain_state.json`），就直接現算現存，之後每分鐘重跑都讀快取。

**還沒回測驗證這個選股組合的實際績效**——2026-10-12只做過一次即時dry-run驗證管線本身能跑
（選到鴻海2317），沒有驗證搭配K棒反轉型態的歷史表現。

## 帳戶前置條件

**現股當沖**：下單帳戶需先向永豐金另外申請並開通「現股當沖」交易權限——跟一般現股買賣是分開的
權限，需要券商審核，不是程式碼能解決的事。沒開通的話，當天買進的股票無法在同一天賣出（會被視為
一般現股交易，次日才能賣），強制平倉會下單失敗。這跟當初下單需要的CA憑證簽署一樣是帳戶層級的
一次性設定，需要使用者自行向永豐金申請。

**融資融券當沖（多空都做）**：`--signal reversal_both`需要**另外的信用交易帳戶**（融資融券權限），
跟現股當沖是分開審核的帳戶層級設定，一樣需要使用者自行向永豐金申請，Claude不會代為處理。此外
融券還受個股本身的融券額度限制（不是所有股票都能融券、額度用完也會被擋），Shioaji下單時若額度
不足會直接被券商端拒單，程式不會事先檢查。

## 檔案結構

- `config.py` — 所有可調參數（ORB時間窗、停損停利%、量增門檻、流動性門檻、強制平倉時間、資金上限、
  觀察清單檔數/權重）
- `minute_data.py` — 用 `api.kbars()` 抓當天分鐘K，算開盤區間高點/低點/幅度/量增比/累積成交金額/最新價
- `watchlist.py` — 每日觀察清單的評分/排序邏輯（流動性+振幅加權），`build_watchlist.py`跟`backtest.py`
  共用；也是快取檔(`watchlist_state.json`)的讀寫介面
- `build_watchlist.py` — 開盤前跑一次的獨立程式：掃全市場、算分、寫快取
- `signals.py` — 進場/出場判斷邏輯，純函式，不碰 Shioaji，可以用假資料單元測試
- `daytrade_monitor.py` — 每分鐘主程式（進場+出場都在這裡），讀`watchlist.py`的快取，不自己掃全市場
- `report.py` — 只在真的有進場/出場動作時才寫入 `trading/daytrade/reports/YYYY-MM-DD.txt`
  （append，不是每分鐘重寫一次）
- `patterns.py` — 三種替代訊號的型態判斷邏輯（K棒反轉/連續同向/滾動範圍突破），純函式可單元測試；
  `evaluate_entry()`是`daytrade_monitor.py`跟`backtest.py`共用的單一進場判斷入口
- `news_watchlist.py` — 新聞選股清單的存取介面（寫入靠Claude手動搜尋，讀取跟`watchlist.py`同一套
  「快取+日期檢查」模式）
- `news_api.py` — 新聞選股的API路線：用cnyes公開新聞API依文章提及次數排序選股，可完全程式化
- `ai_chain_watchlist.py` — 單一個股選股：AI伺服器題材成分股 → 前一天大量門檻 → 新聞熱度最高者
- `backtest.py` — 用歷史分鐘K回測，每個交易日都用「只看得到前一天」的全市場資料重建觀察清單
  （跟`watchlist.py`同一套評分邏輯，避免用到未來資料），並把ORB跟`patterns.py`三種訊號一起跑出
  比較表
